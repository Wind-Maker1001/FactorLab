## Operator procedure after explicit approval

1. Refresh the Demo signing clock, rules, account facts, quotes and order
   identity. Compare the actual credential binding and both durable journals.
   Use a dedicated local protocol and controller `PaperStore` pair outside
   Git. Require the approved limit to remain below the fresh bid and inside
   the mark band, the same quantity to remain the legal minimum, and the
   gateway amount and fee-inclusive reservation to remain within their caps.
   If these checks fail, return a refreshed plan for approval.
2. While both clocks permit writes, bind the exact order intent above to the
   process-local authorization. Use `TradingController` →
   `DemoExecutionGateway` → `DemoFuturesAdapter` → `DemoNetworkTransport`.
   The adapter persists the client ID before dispatch. Submit it once and
   query the same ID. Start cleanup as soon as the order state is known.
3. If unfilled and still open, cancel that ID once and GET-confirm `CANCELED`.
   If partially filled and still open, cancel the remainder once and GET
   the terminal state. Record executed quantity, average fill price, actual
   commissions, remaining position, wallet balance and terminal state. Stop
   after cleanup. If fully filled, record the same reconciliation and stop
   with the resulting position. Any reduce-only close requires a separate
   plan and approval.
4. On an uncertain submission or cancellation, recover with GET by the
   original client ID. A confirmed open order can proceed to its first
   approved cancellation if the authorization still permits it. After an
   uncertain DELETE, continue GET-only recovery and escalate any open order.
   If state remains unknown, stop and report the ID and manual follow-up.
5. At expiry, GET recovery remains available. Any remaining open order
   requires new explicit cleanup authorization. Reconcile account state and
   revoke the capability at the end of the session.

## Offline rehearsal and real request receipt

Binance documents POST and DELETE acknowledgments that can omit `cumQuote`.
The adapter now gets the cumulative quote from Query Order for the durable
client ID when the acknowledgment omits it. If that readback fails, the write
outcome stays UNKNOWN and recovery uses only GET. Regression fixtures model
both successful readback after a partial fill and an initial `-2013` after
an acknowledged POST. [Binance New Order](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/trade#new-order-trade)
· [Binance Cancel Order](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/trade#cancel-order-trade)

The targeted suite passed **91 tests** on Python 3.13.9 and pytest 8.4.2 with socket connects
blocked. It covered plan validation, controller admission, durable identity,
request parameters, idempotency, terminal reconciliation, GET-only recovery,
Kill Switch and Production refusal. A separate offline UTC-expiry scenario
blocked POST and DELETE and still allowed GET. Exact-price and exact-quantity
rehearsals used temporary `PaperStore` files with `OfflineTransport` for
unfilled, partial and full fills. A stubbed HTTP rehearsal showed that a
lost POST reply blocked both the same ID and a second ID, and that the
lifetime one-order cap still applied after GET recovery and cancellation.

Actual Demo traffic for C1 was **14 GETs** (4 public, 10 signed),
**0 POST**, **0 DELETE**, and **0 other methods**. Thirteen GETs returned
HTTP 200. The exact-ID lookup returned HTTP 400 / `-2013` as expected.
